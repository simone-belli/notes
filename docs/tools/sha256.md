# SHA-256

A cryptographic hash function mapping any input to a fixed **256-bit** output — 32 bytes, printed as 64 hexadecimal characters. Part of the SHA-2 family (SHA-224/256/384/512), standardised by the National Institute of Standards and Technology (NIST) in FIPS 180-4. "256" is the output size, not the security level.

```
""       -> e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
"hello"  -> 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
```

## Properties

| Property | Statement | Buys you |
|---|---|---|
| Deterministic | same input → same output, always | content addressing, dedup, caching |
| Fixed size | any input → exactly 32 bytes | cheap to store, index, compare |
| Avalanche | flip one input bit → ~half the output bits flip | no partial information leaks |
| Preimage resistant | given `h`, can't find `m` with `H(m) = h` (2²⁵⁶ work) | publishing a hash is safe |
| Collision resistant | can't find `m₁ ≠ m₂` hashing equal (2¹²⁸ by birthday bound) | a digest *identifies* content |

!!! warning "A hash is not encryption"
    There is no key and nothing to decrypt — the function is lossy by construction. "Cracking" a hash means *guessing* inputs and hashing candidates until one matches, which is exactly why speed is a liability for passwords.

Best published attacks reach collisions on 31 of 64 rounds of a reduced SHA-256; the full function is unbroken after ~25 years. Contrast MD5 (collisions in seconds) and SHA-1 (broken in 2017 by SHAttered, ~2⁶³ work).

## How it works

A **Merkle–Damgård** construction: 512-bit blocks fed one at a time through a compression function that updates eight 32-bit state words.

- **Initial state** — fractional parts of the square roots of the first 8 primes. **Round constants** — cube roots of the first 64 primes. These "nothing-up-my-sleeve" numbers are public evidence that no backdoor was hand-picked into them.
- **Padding** — append a `1` bit, then zeros, then the original message length as a 64-bit big-endian integer.
- **64 rounds** per block, using only AND, XOR, NOT, rotations, shifts and 32-bit addition — no lookup tables, no multiplication. Hence fast in software, tiny in hardware.
- **Feed-forward** — after the rounds, the working variables are *added back* into the previous state. The rounds alone are invertible; this final addition (the Davies–Meyer step) is what makes the whole thing one-way.

## Length extension

Because the digest **is** the internal state, anyone knowing `H(secret ‖ data)` and its length can continue hashing and produce `H(secret ‖ data ‖ padding ‖ anything)` without knowing the secret.

```python
import hashlib, hmac

# BROKEN — an attacker can append data and forge a valid tag
tag = hashlib.sha256(secret + msg).hexdigest()

# Correct: HMAC (Hash-based Message Authentication Code)
tag = hmac.new(key, msg, hashlib.sha256).hexdigest()
hmac.compare_digest(tag, received)   # constant-time, never ==
```

`compare_digest` matters: `==` short-circuits on the first differing byte, and that timing difference leaks the correct tag one byte at a time. SHA-512/256, SHA-3 and BLAKE2/BLAKE3 are immune to length extension by design.

## Computing it

```python
import hashlib

hashlib.sha256(b"hello").hexdigest()          # 64 hex chars
hashlib.sha256(b"hello").digest()             # 32 raw bytes
hashlib.sha256("café".encode()).hexdigest()   # text must be encoded first
```

Streaming — `update()` accumulates, so `update(a); update(b)` equals hashing `a + b`:

```python
h = hashlib.sha256()
with open("big.iso", "rb") as f:
    while chunk := f.read(1024 * 1024):
        h.update(chunk)

# Python 3.11+: same thing, releases the GIL and picks the chunk size
with open("big.iso", "rb") as f:
    digest = hashlib.file_digest(f, "sha256").hexdigest()
```

```bash
sha256sum file.iso            # Linux / GNU coreutils
shasum -a 256 file.iso        # macOS / BSD
openssl dgst -sha256 file.iso # anywhere OpenSSL exists
sha256sum -c checksums.txt    # verify against a published checksum file

echo -n "hello" | sha256sum   # -n matters: echo's trailing newline is part of the message
```

## Where it shows up

- **Content addressing** — [Git](../git/internals.md) names objects by the hash of their content (SHA-1 historically, SHA-256 repositories since Git 2.29); Docker layers use `sha256:` digests. Hashing structured data this way requires a byte-stable encoding first — see [canonical JSON](../python/language/stdlib/json.md).
- **Merkle trees** — hash pairs of hashes up to one root. That root is a *commitment* to the whole dataset in the cryptographic sense: it can't be changed without changing a leaf, yet it still allows O(log n) proofs that a single leaf belongs. Git trees, Bitcoin blocks, Certificate Transparency. (Unrelated to Git's *commit object*, which is one such commitment — a hash over a tree and its parents.)
- **Bitcoin** — proof of work searches for a nonce making `SHA256(SHA256(header))` start with N zero bits; the double hash is a length-extension defence.
- **Transport Layer Security (TLS)** — a certificate authority signs a SHA-256 digest of the certificate, not the certificate itself.
- **JSON Web Token (JWT) `HS256`** — HMAC-SHA-256 over header and payload.
- **Lockfiles** — `poetry.lock`, `package-lock.json`, `pip --require-hashes` pin dependencies by digest, which is what turns a lockfile into a security boundary rather than a version list. See [poetry.md](../python/tooling/poetry.md).

## When not to use it

!!! warning "Never store passwords with SHA-256"
    Its speed is the flaw — a GPU computes billions of SHA-256 per second, so a leaked table of salted digests is brute-forced offline. Use a deliberately slow, memory-hard key derivation function (KDF): **Argon2id** first, else scrypt, bcrypt, or PBKDF2-HMAC-SHA256.

- **Hash tables** — cryptographic strength costs cycles you don't need; xxHash or Python's keyed SipHash are an order of magnitude faster.
- **Verifying downloads from an untrusted source** — a checksum published beside the file proves nothing, since whoever replaced the file replaced the checksum. You need a signature or an out-of-band channel.
- **Small input domains** — hashing an email address or a 6-digit code doesn't anonymise it; the attacker enumerates all candidates.

## Performance

- ~200–400 MB/s per core in software; 1–3 GB/s with hardware acceleration (Intel SHA extensions, ARMv8 crypto extensions), which `hashlib` gets for free via OpenSSL.
- SHA-512 (and SHA-512/256) is often ~1.5× faster on 64-bit CPUs *without* those instructions, since it works on 64-bit words. With them, SHA-256 wins.
- BLAKE3 is several GB/s and parallelises across cores. SHA-256 wins on ubiquity — every language, runtime and hardware security module speaks it.

!!! tip "Mental model"
    A fingerprint for bytes: short, stable, unforgeable, and revealing nothing about what it came from. Every use follows — name things by their fingerprint, prove two parties hold the same bytes without exchanging them, or prove you did work to find a fingerprint of a rare shape.
